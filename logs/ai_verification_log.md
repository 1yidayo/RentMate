## 概述

## Case 1: Extraction Hallucination（擷取幻覺）

### 測試情境
輸入一段格式不完整、缺少關鍵欄位的 Dcard 租屋貼文，
觀察 AI 是否會「補腦」填入原文未提及的數值。

### 原始輸入
```
[請在實際測試後填入：貼入你使用的測試文字]
例如：台大附近套房，三樓，有冷氣，近捷運，生活機能佳，歡迎來電詢問
（刻意不寫租金、坪數、押金）
```

### AI 產生的回答（錯誤版）
```
[請在實際測試後填入：截圖 AI 輸出的 JSON，特別記錄哪些欄位 AI 自行填入了數值]
```

### 錯誤類型
- [x] Hallucination（AI 幻覺 / 補腦）
- [ ] Logic Error
- [ ] Context Loss
- [ ] Prompt Injection

### 錯誤分析
- **AI 為什麼產生這個錯誤？**
  LLM 的訓練目標是生成「看起來合理」的輸出。當輸入資訊不完整時，
  模型傾向於根據統計規律補充「典型」數值，而非承認資訊不足。
  
- **基本 LLM 架構為何無法避免此問題？**
  純粹的 LLM 沒有「對原文進行逐字查核」的機制。
  模型在 decoding 時無法區分「原文有」和「我推測的」，
  兩者對模型來說都只是 token 的概率分布輸出。

### System 2 改善方案
- 建立 `extraction-verifier-server` MCP Server
- Verification Agent 逐欄比對：AI 輸出的每個非 null 值，
  是否能在原始文字中找到對應的字串依據
- 無法找到依據的欄位強制設為 null 並標記警告

## Case 2: Ambiguous Input Misinterpretation（模糊條件錯誤解讀）

### 測試情境
使用者以自然語言描述篩選需求，包含主觀、相對性詞彙
（「近」、「便宜」、「大一點」），觀察 AI 是否用合理的數值解讀。

### 原始輸入
```
[請在實際測試後填入：你輸入的篩選問題]
例如：我要找便宜一點、離輔大近、最好有冷氣的，有沒有推薦？
```

### AI 產生的回答（錯誤版）
```
[請在實際測試後填入：AI 的回答內容，特別標記不合理的數字解讀]
```

### 錯誤類型
- [ ] Hallucination
- [x] Logic Error（模糊詞語的主觀量化錯誤）
- [ ] Context Loss
- [ ] Prompt Injection

### 錯誤分析
- **AI 為什麼產生這個錯誤？**
  「便宜」、「近」都是相對概念，缺乏絕對標準。
  LLM 根據訓練資料的統計平均，可能將「便宜」解讀為全台灣平均，
  而非該區域或該使用者族群（大學生）的合理期待。
  例如：將「便宜」設定為租金 < $8,000，
  但輔大周邊雙人套房均價約 $10,000–$15,000，
  導致 AI 篩出空集合或不合邏輯的結果。

- **基本 LLM 架構為何無法避免此問題？**
  LLM 本身無法動態查詢特定地區的「市場行情」資料。
  它只能依賴靜態訓練知識推估，缺乏即時的地理與市場脈絡。

### System 2 改善方案
- 建立 `preference-server` MCP Server，讓使用者先設定個人基準
  （例如：預算上限、可接受通勤時間、所在學校）
- Orchestrator Agent 先查詢 preference-server，
  再將量化後的條件傳遞給 RAG Agent 進行篩選
- 降低 LLM 對模糊詞語的自行解讀空間

## 測試總結

| 案例 | 錯誤類型 | 嚴重程度 | System 2 解法 |
|------|----------|----------|---------------|
| Case 1 | Hallucination | 高（填入錯誤數據影響比較決策） | Verification Agent 逐欄查核 |
| Case 2 | Logic Error | 中（結果偏差，非完全錯誤） | Preference Server + 量化前處理 |

### 根本原因（共同）
基礎 LLM 架構的核心限制：
1. **無接地性（No Grounding）**：模型輸出不與外部事實資料庫綁定驗證
2. **無不確定性表達機制**：模型傾向輸出確定答案，而非「不知道」
3. **上下文無法持久化**：每次呼叫 API 都是獨立的，無法跨請求記憶使用者偏好
